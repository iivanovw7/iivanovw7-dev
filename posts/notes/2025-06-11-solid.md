#### Why SOLID Matters <a name="Why SOLID Matters"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

**SOLID** is an acronym representing five principles. Principles usually imply rules, restrictions, and a set of actions.
These patterns and principles, approaches, rules, like – SOLID, GRASP, OOP, Gang of Four patterns, DRY etc. may seem like an overwhelming amount of complex information.

However, if we abstract away from all that volume, we can understand that all these principles dictate roughly the same thing:

1. **They allow developers to speak the same language.**
2. **They help to develop maintainable and scalable applications.**

---

#### Speaking the Same Language <a name="Speaking the Same Language"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

The more project-specific knowledge there is, the tougher it is for new developers to get up to speed. That costs both money and time. So, developers are always trying to minimize this project-specific knowledge. They do this by using frameworks, which set up basic structures, and by following design ideas like SOLID and GRASP, which encourage similar coding styles. Plus, approaches like Object-Oriented Programming (OOP) and functional programming help everyone speak roughly the same language across different projects.

#### Addressing Common Problems <a name="Addressing Common Problems"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

Patterns and principles are the same as mathematical formulas, but in the world of programming. Over the years of programming's existence, many problems have been identified in software development, many peculiarities, many nuances. All these nuances are gathered into **patterns and principles** with the help of which we can write **good code**.

---

#### Characteristics of Good Code <a name="Characteristics of Good Code"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

1. **Scalability:** Changes to such a project should be easy to implement. Some projects live for decades. The larger the project, the harder it is to maintain and modify. Well-written code is easily maintained and modified from the outset.
2. **Low Barrier to Entry:** The project-specific knowledge should be minimized. This can be achieved by using basic principles and approaches like SOLID, patterns, and frameworks.
3. **Simplicity:** Not overcomplicated, kept at a simple, understandable level.

## The SOLID Principles <a name="The SOLID Principles"></a>

## 1. Single Responsibility Principle (SRP) <a name="Single Responsibility Principle (SRP)"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

A class should have only one reason to change. In other words, a class should solve only one problem and have a single area of responsibility. This doesn't just apply to classes, it's also applicable to functions, functional programming, and frontend components.

A specific entity solves one problem. We shouldn't have classes or components that simultaneously log something, write something, send something, and display something. This is an anti-pattern known as a **"God object"**, an object with multiple responsibilities and functions.

**SRP is about decomposition.** Each class has one area of responsibility, we decompose everything into modules as much as possible.

#### Why We Need SRP and What Problems It Solves

When entity grows too large, starts solving many problems, we get **tightly coupled code**. If one thing breaks, everything else breaks too, the **readability of such code deteriorates**. If a class has thousand lines, something is clearly wrong with that class.

**Making changes to such a large object/class is time-consuming and expensive.** There are many other reasons why creating large classes and not using decomposition is bad. For example, **version control (Git)**: when many developers modify the same file, it inevitably leads to conflicts and bugs.

#### SRP: Class example

We have some abstract class with a couple of fields and methods to retrieve those fields. Then, the client requests that we can save this entity somewhere (e.g., a database) and send it somewhere (e.g., an API). We, without much thought, immediately add these methods to this class. Two methods, close together, convenient, comfortable.

```typescript
class User {
	id: number;
	username: string;
	password: string;

	constructor(username: string, password: string) {
		this.id = Date.now() * Math.random();
		this.username = username;
		this.password = password;
	}

	send() {}
	get() {}
	save(user: User) {}
	remove(id: number) {}
	logToExcel(user: User) {}
	logToTxt(user: User) {}
	printToPdf(user: User) {}
	printToDoc(user: User) {}
}
```

Then the want to be able to print this entity, and log all actions that happen with this entity. (e.g., "The user changed this entity," or "saved it, and to see the logs in a table immediately.") As a result, we have an object that has some state, and it can save itself, send itself, print itself, and log itself, it becomes a God object.

We realize we're making a mess and move the save or delete method (e.g., from a database) into a separate class called **Repository**. We continue moving forward, deleting the sender from the original class and moving it to an **HTTP** class. Now this class is responsible only for sending objects over HTTP. When we need to add a method to receive an object via HTTP, we'll modify the HTTP class. We won't have to touch the original class at all.

```typescript
class Http {
	send(user: User) {}
	get(id: number) {}
}

class UserRepository {
	save(user: User) {}
	remove(id: number) {}
}
```

Moving further, we create two more classes: one for **logging** and another for **printing**. When a task comes in to fix logging or printing, we don't go into the huge object and dig for hours. We go to a specific class, a specific module, and solve a specific local problem. At this stage, we can even **parallelize** these tasks: give one developer the logging fix and another the printing fix, and no conflicts will arise. Plus, we've separated the data model – objects that contain some state and behavior. Each of our classes is responsible for a specific operation.

```typescript
const getId = () => Date.now() * Math.random();

class User {
	id: number;
	username: string;
	password: string;

	constructor(username: string, password: string) {
		this.id = getId();
		this.username = username;
		this.password = password;
	}
}

class Http {
	send: () => {};
	get: () => {};
}

class UserRepository {
	save(user: User) {}
	remove(id: string) {}
	get(number: string) {}
}

class UserLogger {
	logToExcel(user: User) {}
	logToTxt(user: User) {}
}

class UserPrinter {
	printToPdf(user: User) {}
	printToDoc(user: User) {}
}

class UserController {
	send(user: User) {
		return Http.send();
	}

	get(id: number) {
		return Http.get();
	}
}
```

#### SRP in Code: User and HTTP Data Fetcher

We have a `User` class with a constructor that takes a username and password to create a user object. Then the class grows, and we add many methods to it that are completely unrelated to the class. Ideally, these methods should have been moved to corresponding classes that solve specific problems: `Repository` for saving, `Logger` for logging, and `Controller` for sending.

**Second example:** We have a class called `HttpDataFetcher` with `GET`, `POST`, `PUT`, and `DELETE` methods for making HTTP requests. Then we're told to implement a method to get a user via HTTP. We, without much thought, add a method to this class, use the internal `GET` method, and everything is fine. We have a small, readable class.

Then we're told to create methods to get requisites and a list of clients, and our class slowly starts to grow. Here, of course, the methods are simple, but imagine they have some logic, at least 5-10 lines of code. We slightly improve our code by extracting the `GET`, `POST`, and `DELETE` methods into a separate **`HttpClient`** class, where these methods should logically reside.

Then we improve our code again, breaking down the generic `DataFetcher` into two classes: `UserService` and `RequisiteService`. The first handles logic for working with users (retrieval, creation, deletion), and the second handles logic for working with requisites. Now, each class has its own area of responsibility. The first can even be reused anywhere.

```typescript
class HttpClient {
	get(url: string) {}
	post() {}
	put() {}
	delete() {}
}

class UserService {
	client: HttpClient;
	constructor(client) {
		this.client = client;
	}
	getOneUser(id: number) {}
	getAllUsers() {}
}

class RequisitesService {
	createRequisites() {}
	getRequisites() {}
	updateRequisites() {}
}
```

#### Important Note on SRP: Don't Over-Decompose

It's worth noting that you shouldn't go to extremes here either. Everything should be in moderation.

#### SRP in Frontend Components

Let's consider a frontend component that serves as a **User Profile Form**. Initially, this form consists of four input fields for user details and two buttons for saving and resetting the form. At this point, the component strictly adheres to the Single Responsibility Principle (SRP) because its sole responsibility is to **render the user profile form**.

We then add a title "Edit Profile" and integrate methods for saving and resetting the profile data directly into the component. So far, our User Profile Form component still respects SRP.

Next, we implement **form validation** for the user's contact information. This also remains acceptable within the bounds of SRP.

The challenge arises when a new requirement dictates different validation rules based on whether the user is a **premium member or a standard member**, so we introduce an `isPremium` prop. Consequently, the form now has distinct validation logic depending on the user's membership status. This is still somewhat manageable.

However, the component's original purpose was to display a user profile form for **creation**. Now, imagine the `saveProfile` method contains 10-20 lines of code specifically for creating new user profiles. Unexpectedly, a new requirement comes in to also implement **updating existing user profiles**. This means the component's logic now needs to handle not only creation but also updates and potentially other operations on user profiles. At this juncture, the SRP is clearly violated.

Our component, initially designed simply for rendering a form, has now accumulated a significant amount of logic that can change based on various conditions (e.g., one logic for premium users, another for standard users, and distinct logic for creating versus updating profiles).

```typescript
import React from 'react';

interface UserProfileFormProps {
  onSave: (data: any) => void;
  onReset: () => void;
  title: string;
  isPremium?: boolean;
  isEditing?: boolean;
}

const UserProfileForm = (props: UserProfileFormProps) => {
  const {
    onSave,
    onReset,
    title,
    isEditing,
    isPremium
  } = props;

  // This is a sample component that may be violating SRP.
  // It now handles rendering, validation, and multiple save/update logics.

  const validatePremiumUser = () => { /* Premium user validation logic */ }
  const savePremiumUserHandler = () => {
    validatePremiumUser();
    onSave({});
  }

  const validateStandardUser = () => { /* Standard user validation logic */ }
  const saveStandardUserHandler = () => {
    validateStandardUser();
    onSave({});
  }

  // Logic for creating profiles (now part of UserProfileForm)
  const createProfile = () => { /* Creation logic */ }

  // Logic for updating profiles (now part of UserProfileForm)
  const updateProfile = () => { /* Update logic */ }

  const handleSave = () => {
    if (isEditing) {
      updateProfile();
    } else {
      createProfile();
    }
  };

  const currentSaveHandler = isPremium ? savePremiumUserHandler : saveStandardUserHandler;

  return (
    <form>
      <h1>{title}</h1>
      <input type="text" placeholder="Name" />
      <input type="text" placeholder="Email" />
      <input type="text" placeholder="Phone" />
      <input type="text" placeholder="Address" />
      <button onClick={onReset}>Reset</button>
      <button onClick={currentSaveHandler}>Submit</button>
    </form>
  );
};
```

#### The way following `SRP`: Decompose Frontend Components

To adhere to **SRP**, we refactor the components as follows: We keep the core User Profile Form component as lean as possible. Its primary responsibility is limited to rendering the profile form. Any actions like what happens when the reset or save button is clicked, or what the form's title should be, are determined externally through its props.

We then create two distinct components: `PremiumUserProfileForm` and `StandardUserProfileForm`. Both of these components internally utilize the same base `UserProfileForm`. The crucial difference is that `PremiumUserProfileForm` encapsulates the validation logic specific to premium users, while `StandardUserProfileForm` handles validation for standard users. Notice that the actual logic for saving the form is still passed in from the outside via props.

Continuing this decomposition, we introduce `CreateUserProfileForm` and `UpdateUserProfileForm`. The `CreateUserProfileForm` component contains the specific logic for creating new user profiles and decides whether to render the `PremiumUserProfileForm` or `StandardUserProfileForm` based on membership status. Similarly, `UpdateUserProfileForm` is responsible for updating existing profiles.

This example illustrates that building blocks should perform a single responsibility. In this scenario, the fundamental building block is the `UserProfileForm`, which is now reused in various contexts with different encapsulated logic. While creation And updating might seem similar, the key takeaway is that by adhering to **SRP**, the base component becomes highly reusable, focusing solely on displaying the user profile form. We avoid embedding excessive logic directly into it, instead delegating that logic to other specialized components that reuse the clean `UserProfileForm`.

```typescript
import React from 'react';

interface UserProfileFormProps {
  onSave: (data: any) => void;
  onReset: () => void;
  title: string;
}

const UserProfileForm = (props: UserProfileFormProps) => {
  const {
    onSave,
    onReset,
    title,
  } = props;

  return (
    <form>
      <h1>{title}</h1>
      <input type="text" placeholder="Name" />
      <input type="text" placeholder="Email" />
      <input type="text" placeholder="Phone" />
      <input type="text" placeholder="Address" />
      <button onClick={onReset}>Reset</button>
      <button onClick={onSave}>Submit</button>
    </form>
  );
};

const PremiumUserProfileForm = (props: UserProfileFormProps) => {
  const validatePremiumUser = () => { /* Premium user validation logic */ }

  const saveHandler = () => {
    validatePremiumUser();
    props.onSave({});
  }

  return <UserProfileForm onSave={saveHandler} onReset={props.onReset} title={props.title} />
}

const StandardUserProfileForm = (props: UserProfileFormProps) => {
  const validateStandardUser = () => { /* Standard user validation logic */ }

  const saveHandler = () => {
    validateStandardUser();
    props.onSave({});
  }

  return <UserProfileForm onSave={saveHandler} onReset={props.onReset} title={props.title} />
}

const CreateUserProfileForm = ({ isPremium }: { isPremium: boolean }) => {
  const createProfile = () => { /* Creation logic */ }
  const resetProfile = () => { /* Reset logic for creation */ }

  if (isPremium) {
    return (
      <PremiumUserProfileForm
        onSave={createProfile}
        onReset={resetProfile}
        title="Create New Profile"
      />
    )
  }

  return (
    <StandardUserProfileForm
      onSave={createProfile}
      onReset={resetProfile}
      title="Create New Profile"
    />
  )
}

const UpdateUserProfileForm = ({ isPremium }: { isPremium: boolean }) => {
  const updateProfile = () => { /* Update logic */ }
  const resetProfile = () => { /* Reset logic for update */ }

  if (isPremium) {
    return (
      <PremiumUserProfileForm
        onSave={updateProfile}
        onReset={resetProfile}
        title="Update Existing Profile"
      />
    )
  }

  return (
    <StandardUserProfileForm
      onSave={updateProfile}
      onReset={resetProfile}
      title="Update Existing Profile"
    />
  )
}
```

#### Summary of SRP Benefits

To briefly summarize this principle:

-   We now have separate modules (we've used **decomposition**), and code readability has increased.
-   Making changes to such code has become easier because it's less coupled.
-   We have distinct logical pieces.
-   We've gotten rid of the anti-pattern, mentioned earlier.
-   Now, each entity (not just a class, but also a component or function) encapsulates the solution to a single, specific problem, a single logical piece of code.

This gives us many advantages:

-   We can have **parallel development**.
-   It's easier to **version control** (using Git).
-   It's simpler to **test**, both with automated tests we write ourselves and with the help of QAs.

## 2. Open/Closed Principle (OCP) <a name="Open/Closed Principle (OCP)"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

#### OCP Definition

The **Open/Closed Principle**, or the principle of openness and closeness.

**"Software entities (again, this can be classes, components, modules, functions) should be open for extension but closed for modification."**

Modifying existing, working code is bad for one simple reason: it's already been tested and works, and we have no problems with it. If we do modify existing code, we need to perform **regression testing** to ensure we haven't broken existing functionality.

So, what does this mean for us as developers? You see four software entities that are somehow related. Some entity is a parent, and some entities inherit from that parent. The goal is to **add new functionality not by modifying existing entities, but by adding new entities** through composition and/or inheritance, and implementing new functionality there.

#### Practical Considerations for OCP

It's impossible to use this in 100% of cases because there are bug fixes, various logic corrections, and we will inevitably have to touch old code.

#### OCP with Sorting Algorithms

Let's consider another example where we look at this principle from a slightly different angle. We have a `Person` class, a simple class. We also have another class that includes an array of users; let's call it a storage where we can get users, add them, and perform other operations.

We also have three classes that perform sorting: Bubble Sort, Quick Sort, and Merge Sort. We get a requirement to sort a list of users. We add a new method, again performing delegation, and call the `bubbleSort` method from the Bubble Sort class. Then we do roughly the same for a list of music.

Then we get a requirement: "If the list has fewer than 10 elements, we use bubble sort, because Quick Sort won't offer much benefit on such a small sample." We're like, "Okay," we modify the `PersonList` class and the `MusicList` class, and everything works as it should.

At this stage, there's nothing critical. We've made changes to the code, but they don't break anything; they're predictable and obvious. But there's already a drawback: we've duplicated the condition in two places.

```typescript
class Sort {
	public static sort(array: any[]): any[] {
		return [];
	}
}

class BubbleSort extends Sort {
	public static sort(array: any[]): any[] {
		return array;
	}
}

class QuickSort extends Sort {
	public static sort(array: any[]): any[] {
		return array;
	}
}

class MergeSort extends Sort {
	public static sort(array: any[]): any[] {
		return array;
	}
}

class SortClient extends Sort {
	public static sort(array: any[]): any[] {
		if (array.length < 10) {
			return BubbleSort.sort(array);
		} else if (array.length < 1000) {
			return MergeSort.sort(array);
		} else {
			return QuickSort.sort(array);
		}
	}
}
```

#### Improving OCP with Abstraction

We create a **parent class for all sorting algorithms**. This could also be an interface; it's not that important here. After that, we create an **abstraction**, a "sorting client," which performs these checks internally. Consequently, within our lists, we no longer use a specific sorting algorithm but use this client. If we want to change something, we'll do it in one place. This example leans more towards the last principle, **Dependency Inversion**, but it also fits here.

#### OCP in Frontend: Product Forms

Let's look at an example in frontend development using product details forms. Imagine we have a basic form for adding product information. When we need to include additional fields for digital products, we apply the Open/Closed Principle (OCP). Instead of altering the existing product form component, we create a new component that extends its capabilities.

To illustrate this further, consider polymorphic inputs. We can extend functionality through composition rather than traditional inheritance. We define a shared interface for various product types, and each specific product form component implements this interface. If a new product form needs some of the existing logic from a previous form, we can use delegation, calling the relevant methods from the older component within the new one.

```typescript
import React from "react";

interface ProductFormProps {
  onSave: (data: any) => void;
  onReset: () => void;
  title: string;
}

const ProductForm = (props: ProductFormProps) => {
  const { onSave, onReset, title } = props;

  return (
    <form>
      <h1>{title}</h1>
      <input type="text" placeholder="Product Name" />
      <input type="text" placeholder="Price" />
      <input type="text" placeholder="Description" />
      <input type="text" placeholder="SKU" />
      <button onClick={onReset}>Reset Form</button>
      <button onClick={onSave}>Save</button>
    </form>
  );
};

const DigitalProductForm = (props: ProductFormProps) => (
    <div>
      <input type="text" placeholder="Download Link" />
      <input type="text" placeholder="File Size (MB)" />
      <ProductForm
        onSave={props.onSave}
        onReset={props.onReset}
        title={props.title}
      />
    </div>
  )
```

#### OCP Benefits

-   We **eliminate the need for regression testing** – checking our code to ensure we haven't broken anything.
-   This also means that the **probability of creating an error is lower.**
-   For this principle to work fully, it's necessary to **identify the parts of the system that will change at the earliest stage** and create proper abstractions for them.

### 3. Liskov Substitution Principle (LSP) <a name="Liskov Substitution Principle (LSP)"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

#### LSP Definition

The third principle is called the **Liskov Substitution Principle (LSP)**. Let's start with the definition:

**"Functions/entities that use a base type must be able to use objects of derived classes without any issues or breaking the program's logic."**
Rephrased: **A subclass should extend, not replace, the behavior of the base class.**

#### LSP with Databases

We start with a foundational Database class that includes the basic operations: `Connect`, `Read`, and `Write` data. We might initially add a `joinTables` method directly to this base class, assuming it'll always be relevant.

Next, we create a `MySQLDatabase` class, which extends the capabilities of our base Database. Since `MySQL` is a relational database where data is organized into tables, the `joinTables` method fits perfectly here. It allows us to combine data from different tables as expected.

However, a challenge arises when we introduce `MongoDB` into our project. `MongoDB` is a non-relational database; it stores data in collections and documents, not tables. This means the concept of "joining tables" simply doesn't apply. Unfamiliar with SOLID principles, we might choose to override the `joinTables` method in `MongoDBDatabase` and simply throw an error if it's called.

You can probably foresee the issues this creates. Imagine a part of our application that configures and connects to a database, then performs various operations. Initially, everything works fine with `MySQLDatabase`. But when we switch to `MongoDBDatabase`, the Liskov Substitution Principle (LSP) is violated. LSP states that when working with subclasses, we should be confident that substituting a base class with any of its subclasses won't break the application. In this case, switching from MySQL to MongoDB causes an unexpected error when joinTables is invoked, demonstrating a clear violation of `LSP`.

#### The Right Way: LSP for Databases

In this case, with proper design, it would have been appropriate to do the following:

We create another class that inherits from the base class. From it, we remove the `joinTable` method. This class will be oriented exclusively towards relational SQL databases. Then we create another class, but for NoSQL (non-relational databases), and here, for example, instead of joining tables, we have a `createIndex` method. (This example is a bit stretched, but I think you understand the point.) These databases differ, and only then do we create the initial `MySQL` and `MongoDB` classes.

In such a case, our base class only defines operations that are available for all databases (connection, reading, and writing data). Methods specific to a particular type of database are moved to separate classes.

In this example, when launching the application, we expect some database as input, and whichever database we pass, all of them must have a `connect` method with predictable behavior that **complements, not replaces, the behavior of the base class.** This is the main essence of the Liskov Substitution Principle.

```typescript
class Database {
	connect() {}
	read() {}
	write() {}
	// Problematic: This method assumes relational capabilities
	// joinTables() {
	//    throw new Error("This database type does not support table joins!");
	//}
}

class MySQLDatabase extends Database {
	connect() {}
	read() {}
	write() {}
	joinTables() {}
}

class MongoDatabase extends Database {
	connect() {}
	read() {}
	write() {}
	// This override violates LSP if clients expect joinTables to always work
	// joinTables() {
	//    throw new Error("MongoDB does not support table joins!");
	//}
	createIndex() {}
}

function startApp(db: Database) {
	db.connect();
}

startApp(new MySQLDatabase());
startApp(new MongoDatabase());
```

### 4. Interface Segregation Principle (ISP) <a name="Interface Segregation Principle (ISP)"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

The fourth principle is called the **Interface Segregation Principle (ISP)**. It states: **"Software entities should not depend on methods they do not use."**

This principle is quite closely intertwined with the **Single Responsibility Principle (SRP)** and the **Liskov Substitution Principle (LSP)**. The main idea is to **break down large, "fat" interfaces and software entities into smaller, more specialized ones that solve a single problem.**

Rephrased: **"Clients should not be forced to implement interfaces they don't use."**

#### ISP in Action: Abstract Example

Let's look at a clear example to understand it better. Imagine we have an interface with three methods, and a class that implements it. Then a requirement comes in for another class, which is similar to the first but is missing the third method. If we don't know the SOLID principles, we might just ignore this method, making it `return null` or throwing an error.

Then another requirement comes for a class that differs in the second method. From the name of this principle, it should be clear that we should have **split this large interface into three smaller ones**. Then, we would implement only the necessary interfaces in the classes that need them.

After this visual example, let's repeat the definition: **"Software entities should not depend on methods they do not use."** Therefore, when designing interfaces, it's essential to think them through so they are suitable for a specific client. Creating overly generic solutions is often an **anti-pattern** rather than a good practice.

#### ISP with Server-Side Rendering (SSR)

Example with a server-side rendering application, involving both client and server. Both use a state manager like Redux and create a store. On the server, we render an HTML page. To handle paths and navigation, we need a **router** on both the client and server. However, their operations differ: the client router parses paths to render pages, while the server router mainly navigates between pages.

We create a **common interface** for both server and client routers. Then we create a `Router` class, implement the interface, and include a method for URL parsing, which can be used by both. But then we add a `Maps` method (for page-to-page movement) which is only used on the client. Next, we add a method to bind event listeners, also client-only. Finally, a method to add query parameters to the URL string, which can be used by both client and server.

The result is one large, generalized `Router` class containing unnecessary methods for either the server or the client.

```typescript
interface IRouter {
	parseUrl: (url) => void;
	addQueryParams: (params: Record<string, string>) => void;
	navigate: (route: Route) => void;
	attachEventListeners: () => void;
}

class Router implements IRouter {
	parseUrl(): {};
	addQueryParams(params: Record<string, string>) {}
	navigate(route: Route): {};
	attachEventListeners(): {};
}
```

#### The Right Way: ISP for SSR

A better solution would be to create an `IRouter` interface that only handles URL parsing and query parameter addition. Then, for the client-side router, we could create an `IClientRouter` interface that extends `IRouter` and adds methods like `Maps` and `bindEventListeners`. Similarly, for the server, we might have an `IServerRouter` extending `IRouter` with server-specific routing methods.

This approach ensures that the server-side `Router` class only implements methods relevant to the server, and the client-side `Router` class only implements methods relevant to the client. Each entity depends only on the methods it truly uses.

```typescript
interface Router {
	parseUrl: (url) => void;
	addQueryParams: (params: Record<string, string>) => void;
}

interface HttpRequest {
	get: () => void;
	post: () => void;
	put: () => void;
	delete: () => void;
}

interface TokenStorage {
	addToken: () => void;
	getToken: () => void;
}

class ServerHttp implements HttpRequest {
	delete(): void {}
	get(): void {}
	post(): void {}
	put(): void {}
}

class ClientHttp implements HttpRequest, TokenStorage {
	delete(): void {}
	get(): void {}
	post(): void {}
	put(): void {}
	addToken(): void {
		return localStorage.get("token");
	}
	getToken(): void {}
}

const createDependencyContainer = (router: Router, store, httpRequest: HttpRequest) => ({
	getRouter: () => router,
	getStore: () => store,
	getRequest: () => httpRequest,
});
```

#### Summary of ISP Benefits

To briefly summarize this principle:

-   We **free software entities from methods they don't use**. This leads to more predictable program behavior.
-   The code becomes **less coupled**, which is a key goal in system design

### 5. Dependency Inversion Principle (DIP) <a name="Dependency Inversion Principle (DIP)"></a>

<p align="right">(<a href="#toc">back to contents</a>)</p>

The fifth and final principle is the **Dependency Inversion Principle (DIP)**. Here's how it's defined:

"High-level modules should not depend on low-level modules. Both should depend on **abstractions**. Abstractions, in turn, should not depend on details. Details, in turn, should depend on abstractions."

#### The "Factory" Analogy

Imagine a factory with **workers**, **machines**, and **electricity**. The machines depend on the electricity (think of these as interconnected software entities). Machines also have **parts**.

Let's say a part in one of the machines breaks. We replace the part, and suddenly, the machine's operation logic changes. Now, our workers can't operate it. On top of that, the new part requires different electrical power and voltage.

This is a **violation of DIP**. Our high-level modules (workers) are directly dependent on low-level modules (machine parts, electricity). To put it simply, a small detail like a broken part forced us to change the workers (who now have to adapt to the new machine) and even rework the electricity supply. In programming, this direct dependency would mean manually changing multiple software entities, classes, or modules.

### How to Avoid DIP Violation (The "Factory" Analogy - Continued)

To fix this, we need to introduce **abstractions**:

-   **For electricity:** We introduce a **power supply module**. This power supply module is an **abstraction** that automatically provides the correct voltage and power to any machine. The machines don't directly depend on a specific power source; they depend on the power supply module abstraction.
-   **For workers:** We introduce a **control panel**. Workers learn to operate this control panel, not the machines directly. This means we can swap out any machine, connect it to the control panel, and the workers will continue to interact with the same interface (the control panel), even though the underlying machine might be completely different.

By using the **Dependency Inversion Principle** and adding these abstractions, our high-level modules are no longer directly dependent on low-level, concrete implementations.

#### Real-World Example: Music Application APIs

Let's look at a music application that fetches tracks from different music services.

When we first built it, we decided to get music from **Yandex Music**. So, we directly created and used instances of `YandexMusicAPI` throughout our code.

Later, we wanted to integrate **Spotify**. Without applying SOLID principles, we'd simply add a `SpotifyAPI` class. The problem? We'd have to change not only how we create the API client but also update all the method calls everywhere, as method names likely differ (e.g., `getTracksFromYandex()` vs. `fetchSpotifyTracks()`). Add **VK Music** into the mix, and it becomes a tangled mess of hardcoded dependencies and inconsistent calls.

#### The "Good" Way for Music APIs

To fix this, we apply DIP:

1. **Introduce a common interface:** We create an `IMusicProvider` interface with a generic method like `getTracks()`.
2. **Implement the interface:** Each specific API class (`YandexMusicAPIISP`, `SpotifyAPIISP`, `VKMusicAPIISP`) implements this `IMusicProvider` interface, providing its unique way to `getTracks()`.
3. **Inject the dependency:** Our high-level `MusicClient` module now takes an `IMusicProvider` instance (e.g., in its constructor). It doesn't care if it's Yandex, Spotify, or VK; it only knows it can call `getTracks()`.

This creates a flexible system. If we want to change music providers, we just change which concrete `IMusicProvider` implementation we inject into the `MusicClient` at the application's setup point. The `MusicClient`'s core logic remains unchanged because it always interacts with the stable `IMusicProvider` abstraction. This is **dependency inversion**: the dependency flow shifts from concrete implementations to abstractions.

```typescript
interface MusicApi {
  getTracks: () => void;
}

class YandexMusicApi implements MusicApi {
  getTracks(): void {}
}

class SpotifyApi implements MusicApi {
  getTracks(): void {}
}

class VKMusicApi implements MusicApi {
  getTracks(): void {}
}

class MusicClient implements MusicApi {
  client: MusicApi;

  constructor(client: MusicApi) {
    this.client = client;
  }

  getTracks() {
    this.client.getTracks();
  }
}

const MusicApp = () => {
  const API = new MusicClient(new SpotifyApi())

  API.getTracks()
}

interface HttpClient {}

class Axios implements HttpClient {
  request() {
    fetch
    XMLHttpRequest()
    node-fetch
    node http module
  }
}
```

#### Key Takeaways on DIP

The **Dependency Inversion Principle** helps us build robust and maintainable systems by ensuring:

-   **High-level modules don't depend on low-level modules; both depend on abstractions.**
-   **Abstractions don't depend on details; details depend on abstractions.**

This leads to:

-   **Reduced coupling** between different parts of your system.
-   **Increased flexibility** to change implementations without affecting dependent modules.
-   **Easier testing** as dependencies can be easily mocked or replaced.

DIP, like the other SOLID principles, is all about making your software modules less interconnected and more self-contained, leading to code that's easier to understand, maintain, and evolve.
